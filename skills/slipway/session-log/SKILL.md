# session-log

Writes one file per work session to `.ai/sessions/`. This is a passive,
best-effort record for reviewer context and orchestrator STEP 0 reconciliation
only. Do not treat its generation as a source of truth, routing input,
validation result, pipeline state, or blocker.

Session files are not listed in `.ai/docs/.manifest.md`, are not `AGENT.md`
inputs, are not planning inputs, and must not be consumed by Bosun or Rigger.

## When to invoke

Called by shipwright (after scoped PRD update + doc regen handoff), hullwright
(after bootstrap, rebuild, or partial regeneration), and chronicler (after sync
patches are applied) — see each agent's own contract for the exact invocation
point.

If writing the session doc fails, warn in the calling agent's normal report and
continue. The calling agent's own output contract (docs, changelog, sync report,
or handoff) remains authoritative.

## File naming

`.ai/sessions/{branch-slug}-{topic-slug}-{timestamp}.md`

- branch-slug: current git branch name, slugified (lowercase, hyphens, no
  special characters). If branch cannot be determined, use `unknown-branch`.
- topic-slug: short slug derived from the feature/task description for this
  session (e.g. `checkout-payment-flow`).
- timestamp: `YYYYMMDDTHHmmss`, UTC.

Never overwrite an existing session doc. Each invocation writes a new file,
unique by timestamp.

## Format

```markdown
---
session_id: {branch-slug}-{topic-slug}-{timestamp}
status: active
source_type: pre-build | post-build
branch: {actual git branch name, unslugified}
contributor: {git user.name if available, else "unknown"}
started: {ISO 8601 timestamp}
ended: {ISO 8601 timestamp}
agent_flow: {which agent(s) ran, e.g. "shipwright -> hullwright (partial)"}
topic: "{short human-readable topic}"
---

# Session Summary

{One paragraph, plain language, what this session did and why.}

# Touched Documents

| Doc | Change type | Description |
|---|---|---|
| {doc filename} | additive \| diverged \| removed | {what changed} |

# Touched Units

| Unit type | Unit ID | Doc | Action |
|---|---|---|---|
| FR-ID \| ADR \| endpoint \| field \| section | {exact identifier} | {doc filename} | new \| modified \| removed |

Use the SAME unit identifiers and types already defined in
skills/slipway/doc-merge-resolution/SKILL.md — FR-ID (e.g. FR-021), ADR-NNN,
[method] [path] for endpoints, collection.field for data model fields, and
`##` heading text for fallback sections. This alignment is mandatory: a future
reconciliation feature depends on session docs and the doc-merge-resolution
skill using identical unit identifiers.

Do not invoke conflict resolution, compare units, infer merge decisions, or
invent unit identifiers beyond those rules.

# Notes for Reviewers

{Free text — anything a human merge-reviewer should know that isn't obvious
from the diff. Leave as "None." if nothing applies.}
```

## source_type values

- `pre-build`: generated by shipwright or hullwright — describes what was
  planned/generated at the documentation level, before implementation.
- `post-build`: generated by chronicler — describes what actually happened
  after implementation, including any DRIFT/INTENTIONAL reclassification.

## Status lifecycle

Every session doc starts at `status: active`.

Status transitions to `resolved` only through the orchestrator's STEP 0
Session Reconciliation Check (see `subagents/slipway.md`), and only in these
exact conditions:
- Caulker's headless invocation against this session returns `clean: true`
  for every unit this session touched, OR
- Every blocked unit that referenced this session has been manually resolved
  by the user through STEP 0's interactive escalation.

No other agent, skill, or code path may change a session doc's `status`
field. `session-log` itself never transitions status — it only ever writes
`status: active` on creation, as before.

The `status` field remains local session-note metadata; it still has no
relationship to `.ai/docs/.pipeline-state.md`'s pipeline mode/step tracking,
implementation status, or the `last_reconciled_sessions` list's own gate
behavior for *other* purposes (planning, security audit, etc.) — only STEP 0
reads and writes it.

## Forbidden behaviors

- Never block pipeline progress on session doc generation success or failure.
  If writing the session doc fails, log a warning in the calling agent's normal
  report and continue — the calling agent's own output contract is
  authoritative, not this file.
- Never invent unit identifiers that don't match doc-merge-resolution's existing
  per-doc-type rules.
- Never overwrite an existing session doc — each session gets a new file,
  unique by timestamp.
- Never list session docs in `.ai/docs/.manifest.md` or treat them as source of
  truth docs, planning inputs, or AGENT.md inputs.
- Never transition a session doc's `status` field from within this skill —
  that responsibility belongs exclusively to the orchestrator's STEP 0, per
  the Status lifecycle section above.
