# Examples

This directory contains reference implementations generated by the `bootstrap-from-prd` skill.

## How to use these examples

Examples are reference material only. Use them to calibrate:

- **Writing tone** — direct, declarative, no filler
- **Level of detail** — how much to write per section, per field
- **Document structure** — section ordering, heading style, formatting conventions
- **Consistency patterns** — how a term used in one doc appears in all others

## What NOT to do with examples

Do not copy:

- Product names or domain names
- Service names or service counts
- Architecture patterns or topology decisions
- Technology stack choices
- API paths, field names, or business rules
- ADR content

Unless the PRD you are generating from explicitly requires any of the above.

## Available examples

### `saas-billing/`

A single-service SaaS subscription-billing platform.

Context: one bounded service that owns plans, usage metering, invoices, and payment retry/dunning, generated by the current doc suite. Good reference for:

- Subscription lifecycle management (trials, upgrades, downgrades, cancellation)
- Usage-based billing and metered aggregation flows
- Payment retry, dunning, and invoice state machines
- Single-service scope where the manifest omits topology diagrams

**Files:**

```
saas-billing/
├── AGENTS.md                              — compiled execution rules
└── .ai/docs/
    ├── .manifest.md                        — generated doc suite manifest
    ├── 01-prd.md                          — source PRD
    ├── 02-technical-architecture.md
    ├── 03-service-boundaries.md
    ├── 04-data-models.md
    ├── 05-api-specifications.md
    ├── 06-operational-flows.md
    ├── 07-engineering-standards.md
    ├── 08-architecture-decisions.md
    └── 10-planning-rules.md
```

**Note on omitted docs:** `09-topology-and-architecture-diagrams.md` is intentionally omitted in this example because the manifest-selected suite treats a single-service scope as having no extra queue/cache/integration topology to document. This is expected; do not force the doc back in for similar single-service projects.
